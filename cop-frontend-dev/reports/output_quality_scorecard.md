## 4. 诚实的负面读数（必须与上面一起看）

这份记分卡的分数**显著高于它实际能证明的强度**。理由如下：

1. **用例 3 零区分度。** 两组 6/6。且其断言几乎是在复述 skill 自带 reference 的原文——
   基线不读 skill 也能过。**该用例应当重设计或删除。**
2. **用例 1 的 19 条断言中，10 条两组同过。** 真实区分点只有一个：字典码。
   - skill 侧用 `COP0002`（命中基座白名单 `cop-ucp-ui/src/utils/dictCode.js`）
   - 基线自造 `COP0200`（**全仓 0 命中**，运行期下拉为空）
   - 但基线**主动且准确地**在交付说明里声明了「这是占位码，运行时取不到码值」——
     按「如实告知即可」的公平读法，断言 19 两组都过，**区分度归零**。
   - 因此 skill 的真实优势是「发出去的码能跑」，**不是**「会提醒人」。
3. **基线远强于预期。** 不读 skill 也能独立避开大多数静默失败陷阱。
4. **两条指标口径不一致**：按用例平均 = 87.1%；把 31 条断言汇总成一个池子 = 90.3%（28/31）。
   本文件采用**按用例平均**（更保守，且与 darwin 的 per-prompt 口径一致）。
   差异来源已在本节披露，**不择优选数**。
5. **测量工具本身有噪声。** 评分器已修复 **6 个 bug**（均为测量工具缺陷，非被测代码）：
   大小写敏感误判 `vehicleInsuranceService.js`、`new Blob(` 误命中既有 `commonExport`、
   用交付说明的散文冒充代码证据、`showOperationRecord` 标识符误命中标签用法、
   断言 19 的声明措辞过窄漏掉基线原句、以及断言 19 的误报。
   修 bug 过程中出现过一次**假阳性**（把无关的「字典白名单」提法当成合规声明），已用 6 例矩阵回归修正。
