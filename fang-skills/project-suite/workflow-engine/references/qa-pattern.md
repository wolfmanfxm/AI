# QA Sub-Agent Pattern

> 独立 agent 用 fresh context 审查主 agent 产出，发现盲点。
> 灵感来源：Anthropic doc-coauthoring 的 "Reader Testing" — 用 fresh Claude instance 测试文档。

## 核心原则

**生成者不应是唯一验证者。** 主 agent 在执行过程中积累了上下文偏见（知道"我打算写什么"），无法客观判断"读者看到了什么"。独立 QA Agent 只看产出文件，模拟真实消费者的视角。

## 三明治模式

```
┌─────────────────────────────────────────┐
│ Main Agent (生成产出)                     │
│   analyzer: 7 维度分析                   │
│   generator: 代码生成                     │
│   planner: 9 模块 PLAN                   │
└──────────────┬──────────────────────────┘
               │ 产出文件
               ▼
┌─────────────────────────────────────────┐
│ QA Agent (独立检查)                       │
│   输入: 仅产出文件（不含对话上下文）         │
│   检查: 遗漏、矛盾、断链、空章节、重复       │
│   输出: qa-findings (结构化)              │
└──────────────┬──────────────────────────┘
               │ qa-findings
               ▼
┌─────────────────────────────────────────┐
│ Main Agent (修复)                        │
│   根据 QA 发现修复产出                     │
│   CRITICAL → 必须修复                     │
│   WARNING → 修复或记录原因                 │
│   INFO → 酌情处理                         │
└──────────────┬──────────────────────────┘
               │ 修复后产出
               ▼
┌─────────────────────────────────────────┐
│ Reviewer Agent (可选，仅 Full 模式)        │
│   输入: 修复后产出 + qa-findings          │
│   验证: QA 发现是否已正确修复               │
│   输出: qa-report.md (最终质量报告)         │
└─────────────────────────────────────────┘
```

## QA Agent 通用 Prompt 模板

```markdown
你是独立 QA 审查员。你的任务是检查以下产出文件的质量。

## 重要约束

- **只基于产出文件做判断**。你没有参与生成过程，也不知道生成者的意图。
- **不要猜测**。如果某处内容不完整，标注为"不完整"，不要推断应该是什么。
- **做消费者的代言人**。模拟一个第一次读这些文件的开发者会遇到的困惑。

## 输入

产出文件列表：
{file_list}

请逐个文件阅读，然后回答以下问题。

## 检查清单

### 1. 遗漏（Completeness）
- 是否有应该覆盖但没覆盖的模块/维度/功能？
- 是否有文件只写了标题但没有实质内容？
- 是否有关键信息（如依赖关系、数据流向）被省略？

### 2. 矛盾（Consistency）
- 跨文件中是否有互相矛盾的描述？
  - 例如：A 文件说模块 X 依赖模块 Y，B 文件说模块 Y 已废弃
- 术语使用是否一致？
  - 例如：同一概念在不同文件中用了不同名称

### 3. 断链（Reference Validity）
- 是否有引用不存在的文件路径？
- 是否有指向不存在章节的内部链接？
- 是否有引用不存在的 API/组件名称？

### 4. 内容质量（Content Quality）
- 是否有空白章节（有标题无内容）？
- 是否有占位符或 TODO 标记？
- 是否有跨文件的大段重复内容（>80% 相似）？

### 5. 可理解性（Comprehensibility）
- 一个不熟悉此项目的新开发者能否理解核心概念？
- 是否有术语在使用前未定义？
- 是否有模棱两可的描述（"可能"、"大概"、"应该"过度使用）？

## 输出格式

返回 JSON（不要 markdown 包裹）：

{
  "findings": [
    {
      "severity": "CRITICAL|WARNING|INFO",
      "category": "completeness|consistency|reference|content|comprehensibility",
      "file": "相对于项目根的路径",
      "location": "章节名或行号",
      "description": "具体的发现描述",
      "evidence": "引用原文中的具体段落（如有）",
      "suggestion": "可操作的修复建议"
    }
  ],
  "overall_assessment": "PASS|NEEDS_FIX|BLOCKED",
  "summary": "一句话总结"
}
```

## 各 Skill 的 QA 检查重点

| Skill | QA 重点 | 特别关注 |
|-------|---------|---------|
| **analyzer** | 知识库完整性和一致性 | 7 个维度是否全部覆盖？跨文件的术语是否统一？统计数字是否自洽？ |
| **generator** | 代码模式正确性和复用 | 是否重复生成了已有组件？import 路径是否存在？模式是否与项目约定一致？ |
| **planner** | 计划逻辑一致性 | 9 模块是否完整？依赖是否有循环？AC 是否可验证？估时是否合理？ |
| **architect** | 决策链完整性 | ADR 四段是否完整？对比矩阵是否有遗漏方案？选型理由是否充分？ |
| **reviewer** | 审查覆盖完整性 | 五轴是否全覆盖？file:line 引用是否有效？分级是否合理？ |
| **tester** | 测试覆盖完整性 | AC 是否逐条覆盖？边界条件是否覆盖？测试是否能实际运行？ |
| **refactorer** | 重构安全性 | 测试是否保持绿色？指标是否确实改善？范围是否受控？ |
| **documenter** | 文档准确性 | 源码引用是否正确？风格是否一致？是否有编造内容？ |
| **releaser** | 发布安全性 | 全链路 confidence 是否达标？Breaking change 是否有迁移说明？回滚方案是否完整？ |

## 使用时机

| 场景 | QA Agent | Reviewer Agent |
|------|----------|----------------|
| 日常使用 | ✅ 始终启用 | ❌ 跳过 |
| 关键任务（生产部署前、重大重构） | ✅ 始终启用 | ✅ 启用 |
| 快速迭代 | ⚡ 仅检查 CRITICAL（缩短 prompt） | ❌ 跳过 |
| Token 紧张 | ⚡ 仅检查 completeness + reference | ❌ 跳过 |

## 成本考量

- QA Agent: 额外 1 次 agent spawn + 产出文件的总 token 数（约增加 20-40% token 消耗）
- Reviewer Agent: 额外 1 次 agent spawn（约再增加 10-20%）
- 完整三明治（QA + Reviewer）比纯主 agent 多约 40-60% token

**何时值得：**
- 产出会被多人/多项目复用（analyzer 的知识库）→ 始终启用 QA
- 产出直接影响生产行为（generator 的代码、releaser 的版本号）→ 始终启用 QA
- 产出是一次性任务产物（单次 review、单次 test）→ 可以跳过 Reviewer
