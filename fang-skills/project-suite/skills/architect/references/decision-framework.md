# Decision Framework — Architect

> 架构决策记录（ADR）的格式、时机和判定框架。

## ADR 格式

每个架构决策遵循统一格式：

```markdown
## ADR-{NNNN}: {标题}

**状态**: 提议 / 已采纳 / 已废弃 / 已替代
**日期**: YYYY-MM-DD
**决策者**: {角色或"architect skill"}

### 背景

为什么需要做这个决策？当前面临什么问题或选择？

### 决策

选择了什么方案？

### 候选方案

| 方案 | 优点 | 缺点 |
|------|------|------|
| A | ... | ... |
| B | ... | ... |

### 后果

#### 正面
- ...

#### 负面/风险
- ...

#### 迁移策略（如涉及）
- ...
```

## 何时记录 ADR

| 决策类型 | 记录？ | 原因 |
|---------|--------|------|
| 技术选型（框架/库/工具） | ✅ 必须 | 影响面大，后来者需要了解为什么选这个 |
| 架构模式（分层/微服务/事件驱动） | ✅ 必须 | 项目的基础骨架 |
| API 设计约定（REST vs GraphQL） | ✅ 必须 | 影响所有接口 |
| 命名约定 | ❌ | 属于 conventions，不是架构决策 |
| 目录结构 | ⚠️ 可选 | 如果偏离了常见约定才需要记录 |

## 决策时机

```
发现需要决策的点
  ↓
能否推迟到有更多信息后？
  YES → 推迟，先做不影响该决策的工作
  NO  ↓
信息是否足够做决定？
  NO  → 做 PoC/技术验证 → 收集信息 → 再决策
  YES ↓
做决策，记录 ADR
```

## 决策陷阱

| 陷阱 | 症状 | 对策 |
|------|------|------|
| 过早优化 | "未来可能需要支持百万并发" | 基于当前需要选，预留扩展点，不提前实现 |
| 简历驱动 | "我想用这个新技术" | 问：对项目有什么好处？团队能维护吗？ |
| 分析瘫痪 | 对比了 10 个方案还在犹豫 | 限时做决定，5 个候选够用 |
| 过度设计 | "我们可以做成可插拔框架" | 当前有 1 个实现，不需要框架 |
