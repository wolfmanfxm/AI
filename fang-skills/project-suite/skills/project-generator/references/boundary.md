# 职责边界

> generator 只写代码，不做设计也不做审查。

| ✅ 本阶段职责 | ❌ 禁止操作 |
|-------------|-----------|
| 根据 PLAN.md + ARCHITECTURE.md 生成代码 | 做需求拆解（那是 planner 的职责） |
| 遵循项目模式，复用已有组件 | 做技术选型（那是 architect 的职责） |
| 自检：loading/error/empty/类型 | 重新分析项目（那是 analyzer 的职责） |

**缺少 PLAN.md/ARCHITECTURE.md 时**：不应跳过直接生成，提示用户先执行上游 skill。
**小点修改例外**：单文件、无架构影响可直接操作。

## 沙箱边界（硬性，最高优先级）

| ❌ 禁止 | 为什么 |
|--------|--------|
| **运行任何 git 命令**（checkout / status / diff / clean / add / commit / stash / reset / push） | generator 只读写文件，不碰 git。即使「清理自己刚写的改动」也不许 `git checkout -- .`——这是常见越界。真需要还原，交给用户或用 Edit 手动改回。 |
| **访问工作目录以外的任何目录** | 只改当前项目文件，禁止软链/读取兄弟项目 node_modules。 |

## 反例黑名单

| # | ❌ 反模式 | 为什么不要做 | ✅ 正确做法 |
|---|---------|-------------|-----------|
| 1 | **缺少 PLAN.md 就直接生成大型功能** | 无规划导致范围蔓延 | 提示执行 `/project-planner` |
| 2 | **不检查代码存在性就生成** | 重复生成已有组件/API | 先 grep 函数名/组件名，标注状态；**若需求已被现有组件完整覆盖 → 零改动，不新建重复组件** |
| 3 | **生成代码后不做完成报告** | PLAN 与实际偏差被遗忘 | 输出 plan vs actual 对比表 |
| 4 | **不读 patterns/ 就直接生成** | 凭框架通用知识而非项目约定编码，例如用原生表单组件而非项目要求的 <统一表单封装> | 生成前必须加载 patterns/form.md + experience/ |
| 5 | **跳过自检清单直接提交** | loading/error/empty/类型边界未处理，defineOptions(name) 遗漏 | 按 references/self-check.md 逐项跑完再输出完成报告 |

## 失败兜底

| 触发条件 | 一线修复 | 兜底 |
|---------|---------|------|
| context.json 缺 REQUIRED 字段 | 🔴 BLOCK 拒绝执行 | 提示运行 analyzer |
| PLAN.md 缺失 | 标注"⚠️ 无规划"，降级通用模式 | 不阻塞简单修改 |
| 参考实现不存在 | 搜索同类文件，扩大范围 | Element Plus 原生降级 |
| 生成代码与已有冲突 | 标注差异，让用户选择 | 覆盖 / 合并 / 跳过 |
| 知识库不存在 | 降级通用模式 | 标注"⚠️ 未找到项目知识库" |
| 需新增依赖 | 标注 `TODO: 安装依赖` | 不修改 package.json |

## 常见借口（Common Rationalizations）

| # | LLM 会说的借口 | 为什么拒绝 |
|---|---------------|-----------|
| 1 | 「这个组件很简单，不需要查知识库」 | → 仍然 Query |
| 2 | 「已经有类似代码了，直接复制改一下」 | → 仍然走完整验证流程 |
| 3 | 「loading/error 状态没必要，先写 happy path」 | → 全状态覆盖是硬要求 |
