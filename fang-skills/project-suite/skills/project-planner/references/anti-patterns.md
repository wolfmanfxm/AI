# Anti-Patterns — Planner

> 执行 planner 时的禁止操作，每条基于真实踩坑记录。

## 通用反例

| # | ❌ 不要做 | ✅ 正确做法 |
|---|----------|-----------|
| 1 | 跳过 CHECKPOINT 直接输出完整 PLAN | 确认需求理解后再拆解 |
| 2 | 任务粒度过粗（一个任务 5+ 人天） | 超过 2 人天必须拆分 |
| 3 | 任务粒度过细（每个 0.1 人天） | 合并为有意义的单元 |
| 4 | 依赖只标不解释 | 标注依赖类型（硬/软/外部）+ 原因 |
| 5 | 给精确到小数点的工时 | 用 t-shirt size + 人天区间 |
| 6 | 不考虑未知因素直接给无 buffer 估算 | 加 20-30% buffer |
| 7 | 只列任务不提风险 | 每个风险标注可能性+影响+缓解 |
| 8 | 人工分配（"张三做 T1，李四做 T2"） | 不感知团队成员，只标注所需技能 |
| 9 | 忽略下游 skill 需要的信息 | 确保 PLAN.md 包含架构决策点、测试范围 |

## 边界处理反例

| # | 反模式 | 为什么不要做 | 正确做法 |
|---|--------|-------------|---------|
| 1 | 需求不清晰时猜测补齐 | 猜错导致任务列表无效 | AskUserQuestion 澄清关键歧义 |
| 2 | 单任务包含"前后端都做" | 前后端技能不同、节奏不同，合并后无法独立分配 | 按层拆分 |
| 3 | 所有任务都标 P0 | 失去优先级意义，团队无法决策 | 严格区分：P0 阻塞 / P1 核心 / P2 增强 |
| 4 | 风险只写"技术难度高" | 太模糊，无法采取行动 | 具体描述：哪个环节、什么原因、缓解步骤 |
| 5 | 忽略 analyzer 的 .project-knowledge/ | 不了解现有模块边界就拆任务，拆出来的任务可能在错误的模块 | 先读 index.md 了解模块划分 |
