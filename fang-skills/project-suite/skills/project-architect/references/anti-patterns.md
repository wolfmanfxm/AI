# Anti-Patterns — Architect

> 执行 architect 时的禁止操作。

## 通用反例

| # | ❌ 不要做 | ✅ 正确做法 |
|---|----------|-----------|
| 1 | 不读 .project-knowledge/architecture/ 就开始设计 | 先了解现有架构，设计要兼容现状 |
| 2 | 技术选型只推荐一个方案不给对比 | 列出候选 + 维度对比 + 为什么选这个 |
| 3 | 给出决策但不记录理由 | ADR 格式，决策和理由一起保存 |
| 4 | 忽略团队能力做"最优选型" | Elixir 性能好但团队全写 Java → 不选 |
| 5 | 为未来不确定的需求做设计 | YAGNI — 当前需求 + 可预见扩展 |
| 6 | 模块划分只看技术不看业务 | 按领域/业务能力划分，不是按技术层 |
| 7 | API 设计不考虑项目已有模式 | 读 api/request.md，与现有 API 风格一致 |

## 技术选型反例

| # | 反模式 | 正确做法 |
|---|--------|---------|
| 1 | 按 GitHub Star 数选方案 | Star ≠ 适合项目，加上团队/生态/许可等因素 |
| 2 | 选最新的版本（v0.x） | 生产项目优先选稳定版本（v1+） |
| 3 | 忽略许可证问题 | GPL/AGPL 在商业项目可能有问题 |

## 模块设计反例

| # | 反模式 | 正确做法 |
|---|--------|---------|
| 1 | 按技术层拆分（controllers/ services/ models/） | 按业务领域拆分（auth/ order/ product/） |
| 2 | 微服务拆分过早（单体都没稳定） | 先单体/模块化单体，拆分时机是单体成为瓶颈 |
| 3 | 循环依赖容忍 | 严格单向依赖，双向→引入接口/事件解耦 |

## API 设计反例

| # | 反模式 | 正确做法 |
|---|--------|---------|
| 1 | GET 请求修改数据 | GET 幂等，修改用 POST/PUT/DELETE |
| 2 | 动词 URL（`/getUsers` `/createOrder`） | 名词 URL + HTTP 方法：`GET /users` `POST /orders` |
| 3 | 响应结构不统一 | 所有响应统一 `{ data, error, meta }` |
