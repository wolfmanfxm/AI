# 职责边界

> architect 只做设计，不写代码。

| ✅ 本阶段职责 | ❌ 禁止操作 |
|-------------|-----------|
| 技术选型、模块设计、API 契约 | 修改任何代码文件 |
| 输出 ARCHITECTURE.md（ADR 格式） | 做需求拆解（那是 planner 的职责） |
| 评估候选方案、记录决策理由 | 实现代码（那是 generator 的职责） |

**发现代码与设计不符时**：记录在 ARCHITECTURE.md，标注 `[需对齐]`，不直接修改。
**用户要求"开始写代码"时**：引导执行 `/project-generator`。

## 反例黑名单

| # | ❌ 反模式 | 为什么不要做 | ✅ 正确做法 |
|---|---------|-------------|-----------|
| 1 | **跳过现状核实直接出设计方案** | 对已实现功能重复设计 | 先读源码 50 行，标注 `[已实现][部分实现][未实现]` |
| 2 | **PLAN.md 的任务全当成新需求设计** | PLAN 可能未探查代码，高估范围 | 核对 PLAN vs 代码现状，过滤已完成的 |
| 3 | **设计方案里直接写代码实现** | 越界到 generator | ADR 只写设计+契约，不写 .vue/.ts |
| 4 | **ADR 引用的 API/组件在代码中不存在** | 设计基于文档/假设而非实际代码 | 现状核实阶段 grep 确认每个引用的 API 函数+组件路径存在 |
| 5 | **推荐已废弃的模式** | 未读 patterns/ 中的 DEPRECATED 标记（如 el-form 标记为废弃但仍被推荐） | 读 patterns/ 文件时检查"DEPRECATED""废弃""推荐"标记，避免推荐旧模式 |
