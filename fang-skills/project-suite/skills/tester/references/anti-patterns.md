# Anti-Patterns — Tester

> 执行 tester 时的禁止操作。

## 通用反例

| # | ❌ 不要做 | ✅ 正确做法 |
|---|----------|-----------|
| 1 | 不检测测试框架就按默认写 | 读 package.json + 现有测试文件 |
| 2 | 为覆盖而写无意义的测试 | 每个测试验证一个有意义的行为 |
| 3 | 测试函数名用 `test1` `test2` | 描述性名称："应该在[场景]时[行为]" |
| 4 | Mock 被测函数内部的工具函数 | 只 mock 外部依赖 |
| 5 | 测试依赖执行顺序 | 每个测试独立，互相不影响 |
| 6 | 只测 happy path | P0 覆盖正常+边界，P1 覆盖异常 |
| 7 | 不读被测代码就写测试 | 先理解逻辑，再写测试 |
| 8 | 测试失败不分析直接改测试 | 可能是测试写错，也可能是发现了 bug |

## Mock 反例

| # | 反模式 | 正确做法 |
|---|--------|---------|
| 1 | `vi.mock('./utils')` mock 项目内部工具函数 | 内部函数用真实实现 |
| 2 | Mock 了整个模块但只用了 1 个函数 | 只 mock 需要的方法 |
| 3 | 忘记 `vi.clearAllMocks()` | 每个 describe 后清理 |

## 断言反例

| # | 反模式 | 正确做法 |
|---|--------|---------|
| 1 | 只 expect 一个属性，不检查关键字段 | 检查所有影响行为的输出 |
| 2 | `expect(x).toBeTruthy()` 过于宽松 | 精确断言：`expect(x).toBe(true)` |
| 3 | 不 expect 异常情况 | 异常路径也要有断言 |
