# Anti-Patterns — Documenter

> 执行 documenter 时的禁止操作。

## 通用反例

| # | ❌ 不要做 | ✅ 正确做法 |
|---|----------|-----------|
| 1 | 编造不存在的 API 参数或返回值 | 只写代码中确实存在的内容 |
| 2 | 从函数名推测复杂业务逻辑然后写进文档 | 不确定的标注 `[待补充]` |
| 3 | 覆盖已有文档中的人工内容 | 对比差异，只更新自动生成部分 |
| 4 | 不读已有文档就开始写（风格不一致） | 先读 1-2 份，模仿其风格 |
| 5 | 为每个文件生成独立文档（过度文档化） | 只文档化公共接口和关键模块 |

## API 文档反例

| # | 反模式 | 正确做法 |
|---|--------|---------|
| 1 | 把内部实现细节写入 API 文档 | 只写调用方需要的：参数 + 返回值 + 错误 |
| 2 | 不从代码提取，凭对话记忆写 | 每次打开源文件确认后写 |
| 3 | JSDoc 有描述但不用，自己重写 | 优先使用 JSDoc 的描述 |

## README 反例

| # | 反模式 | 正确做法 |
|---|--------|---------|
| 1 | 覆盖已有的手写章节（团队/贡献者/致谢） | 保留人工编写的内容 |
| 2 | 编造不存在的 scripts 命令 | 从 package.json scripts 提取 |
| 3 | 用默认模板完全替换已有 README | 对比更新，不整篇替换 |
