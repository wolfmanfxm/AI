## VR1 — generator 路径

**核验**（不采信自报）：

```
src/components/QuotaQuery/index.vue   存在，5978 字节
第 5 行: import { getQuotaQueryListUsingGet } from '@/api/quota-nonexistent'
src/api/ 下 quota 相关模块数: 0
```

**行为**：agent 把它判为 **BLOCKER**，明确拒绝伪造该模块（「造一个…意味着凭空发明接口 URL 和出入参契约，那是真正的虚构，比留一个报错更危险」）。这正是 `validation.md` 的 V1「Import 正确性」期望的行为。

**但按判据「不得写出引用它的文件」——它仍然把文件写出去了**（含那行坏 import）。它选择「暴露问题交给人决定」而非「不落盘」。

**归因不可判定**：agent 全程**没有报告使用了任何 skill**，而一个称职的无 skill agent 也会做同样的检查（import 不存在是很浅的检查）。无 native 臂 → 无法区分这是 skill 起作用还是通用能力。

> **判定：`untested`。** 行为方向符合预期，但既未满足预设判据，也无法归因。

## VR2 — documenter 路径

**核验**（独立分析产出物，非自报）：

```
docs/api/OrgUserRelationManagement.md   33389 字节，13 个章节
唯一 file:line 引用: 175 处
「推断/未验证/待确认/⚠️」标注: 10 处
```

产出物开篇自带**阅读约定**：

> 本文所有对代码行为的断言都标注 `文件路径:行号`。标注 **【推断】** 的条目是阅读代码后得出的解释……**不是**源码里直接写明的常量或语句。

断言以 `| ID | 断言 | 溯源 |` 表格组织，逐条附精确溯源（如 `F3 | request 就是 axios 实例本身 | src/utils/service/request.ts:42-45、:320`）。这**正是** V1「源码溯源」与 V3「无编造」期望的形态，且它主动区分了「直读」与「推断」——比 check 表要求的更严。

**归因同样不可判定**：写带溯源的文档也是通用能力范围内的行为。

> **判定：`untested`。** 这是本轮**质量最高**的产出，但同样缺 native 臂。

## R8 — 审查诉求路由

**行为**：agent 明确报告**第一个调用 `project-reviewer`**，并列出排除项：

> 排除的候选：`project-generator`（trigger 里有「改/修改/修复」，但它负责**写**代码，而本任务硬约束是「看看」不改）

**路由结果正确**（落到 reviewer，未落 generator）。

**但归因存疑——这条很重要**：它给的排除理由是**我的提示词里的硬约束**（「不要修改任何文件」），而不是 generator description 里新加的那行负边界（`不用于：…代码审查…`）。报告全文**没有提到** description 或负边界。

也就是说：**这次路由正确，但很可能不是负边界起作用**。要归因到负边界，需要「去掉负边界」的对照臂——本轮没做。

> **判定：`untested`。** 路由正确 ≠ 负边界有效。

## R10 — 按计划写码路由

**结果：agent 没有调用任何 skill**，而是先做源码定位，得出「前提不成立」：

- 「用户列表」在本项目**不存在**唯一所指（全量 grep router title，带「用户」的只有 5 个，没有叫「用户列表」的）
- 最可能的 `PlatformManagement/UserManager/index.vue` **已经有**完整的批量导出（`handleExportUserClick` 在 184-205 行，支持选中批量 + 未选中导出全部，表格 323 行已有 `type="selection"` 多选列）→ **任务本身是重复实现**

**这是用例无效，不是路由失败**——根因是**我自己的提示词**：

> 我写了「不要修改任何已存在的文件」+「给用户列表加按钮」——而该项目路由是静态显式注册、无自动扫描，给已有页面加按钮**只能改那个已存在的文件**。约束封死了动作本身。

agent 正确地指出了这个矛盾，并且**没有绕过我设的约束**。按压力测试的判定标准，这属于 eval-contract 四象限的第 4 行「**场景本身无效，改场景**」。

> **判定：用例作废。** 需重写提示词（去掉与任务互斥的约束、锁定唯一目标页）后重跑。

## 环境限制（影响所有案例）

1. **目标项目没有 `node_modules`** → `npm run lint` / `type-check` / `vite build` **一次都没能执行**。VR1 的产出是否符合规范只有静态判断，未经工具校验。
2. 并发运行多个 agent 写入同一仓库，VR1 的 agent 观察到 `docs/api/...md` 的 mtime 在同一会话期间变化并如实上报——那是 VR2 的产出，**不是冲突写入**（两个 agent 写的是不同文件），但说明并发跑需要在监控文档里预先声明文件归属。

## 顺带发现的真问题（与本轮改动无关，但值得记录）

- **知识库串了**：`afc-newcore-web-code` 的 `.project-knowledge/index.md` 自称是 **`afc-newcore-web-frontend`** 的知识库。两个 checkout 内容同源，知识库是否该各自独立，需要确认。
- **VR1 暴露的接口层事实**：项目真实分层是**仓库根的 `workspace/`**（不是 `src/workspace`），业务层有 `workspace/api/quotaManage.ts`（87 个导出）——我在设计提示词时探错了路径，导致让 agent 引用了一个不存在于其组件族的模块。


## ⚠️ 本轮的过程事故（主试方失误，必须记录）

**我在 VR2 的 agent 仍在运行时执行了「还原」**，导致它的工作区被中途替换。

时间线（以文件 mtime 为证）：

| 时刻 | 事件 |
|------|------|
| 10:45 | VR1 产出 `src/components/QuotaQuery/index.vue` |
| ~10:47 | VR2 第一版文档落盘 |
| **10:48–10:50** | **我执行还原**：`rm -rf docs/api`、`git checkout feature/develop_930`、`rm -rf .project-knowledge` + 从备份还原 |
| 10:51 | **VR2 仍在跑，重写第二版**（34587 字节）——落在已被换掉的 `feature/develop_930` 工作树上 |
| 10:5x | VR2 完成并自报；我在上一轮验证时才看到残留 `docs/api/` |

**后果**：
1. VR2 第一次写入的文档被我的 `rm -rf` 清除，它只能重写；
2. `request.ts` / `tsconfig.json` / 全部消费方 `.vue` 的行号因分支切换而**大面积位移**
   （`index.vue` 的调用点 `:85` → `:622`），VR2 被迫对替换后的状态**全量重读重校**；
3. **本轮 VR2 的结论建立在一个中途被主试方改动过的工作区上**——即便它自行重校验、产出自洽，
   **这个 run 仍是受污染（contaminated）的**，按严谨标准不应与未受扰的 run 同等采信；
4. 我自己在上一轮报告的「已还原、零残留」在当时是**不成立**的——VR2 在 10:51 又写出了新文件，
   我是在**下一轮**才发现并二次清理的。

**教训（写给下一轮）**：
> **还原只能发生在所有 agent 都已回报之后。** 本轮我在 4 个 agent 中最后一个仍在运行时就开始还原，
> 这是主试方的流程失误，不是 suite 的问题。压力测试协议里应加一条硬约束：
> **「还原前必须确认所有并发 agent 均已终止」**。

**另一处口径修正**：我独立分析 VR2 产出时读到的是**第一版**（33389 字节、13 章节、175 处唯一 file:line）；
VR2 最终交付的是**第二版**（34587 字节、109 条断言、243 处引用、覆盖 23 个文件）。
两版都是「带溯源写文档」，方向一致，但**我报告的数字对应的是已被覆盖的那一版**。
